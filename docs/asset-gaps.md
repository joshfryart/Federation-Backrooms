# Asset gaps: what the ship's company still has no model for

Scope: 3D props, wall fixtures, hand-held items, carts, wearables, animation clips, signage and icons that the game's own code and data
refer to but that are drawn today as a stand-in, a generic box, or nothing. Written for the agents who build the next art batches.
Original designs only (homage project: no franchise names, marks or silhouettes). Where a code id still carries a borrowed word
(`warpcore`, `padd`, `tricorder_*`, `phaser*`, `hypospray`), this document quotes the id in backticks and gives the asset a neutral name.

## 1. Method

1. **Inventory of what exists** (read from code, not from memory):
   - Floor props: `buildProp` in `js/world.js:233-369`, 32 kinds in `PROP_KINDS` (`js/world.js:1321`): console, chair, viewscreen, warpcore, shuttle, holocube, pad, bunk, table, biobed, crate, tree, lonechair, plant, cart, replicator, desk, cell, weaponrack, treadmill, weightbench, labbench, washer, sofa, lathe, workbench, tank, drawers, servers, shelving, suitrack, sinkunit. Unknown kinds draw a 0.8 m metal cube (`js/world.js:367`).
   - Wall fixtures: `DECOR` in `js/world.js:460-492`, 22 kinds: locker, shelf, monitorB/O/G, medcab, gauges, pipes, toolboard, hose, rack, picture, mirror, planter, coil, menu, extinguisher, comm, fountain, ventgrille, breaker, kit. Per-room pools in `ROOM_DECOR` (`js/world.js:493-500`).
   - Which prop goes in which room: `js/gen.js:97-124` (one `case` per room type).
   - Item art: `js/itemart.js`, 49 kinds (`ITEM_KINDS`, list in `docs/itemart.md`), hooked up for pickups, clutter and held items (`js/world.js:876`, `js/carry.js:30`, `js/actors.js:394`).
   - Handhelds: `js/handhelds.js`, 23 rows, each with a `model` that is one of the 49 item kinds.
   - Carry items and carts: `js/equipment.js:180` `ITEMS` (37 ids), `CARTS` (cargo, med, tool; meshes in `js/carry.js:118` `makeCart`), `HAULERS`.
   - How furniture is used: `EQUIPMENT` in `js/equipment.js:24-98` (39 entries) and `SPOT_ALIAS` (`:100`).
   - System hardware: `js/sysview.js` (one wall junction box `makeJunction`, one status beacon); `SYSTEMS` in `js/crew.js:83-105` (21 systems, 9 of them hosted on a `junction`).
   - Rooms: `js/data.js` `ROOMS`, 25 keys (24 rooms plus `jefferies`).
   - Bodies: `assets/models/` has `crew_m`, `crew_f`, `crew_f2`, `crew_heavy`, `suit`, `human_anims` (19 clips, listed in `TODO.md:53`); uniforms are three division tints (`js/humans.js:10`).
   - Creatures: `MODELS` in `js/enemies.js:52-59` (gronk, crazed, slimeling, drone, phantom, clinger).
   - Icons: `ICONS` in `js/icons.js:27`, 133 glyphs.
2. **What each billet is scripted to use**: every `duty_loops`, `daily_template`, `activities`, `mission_tasks` and `alert_responses` entry in the 41 `docs/crew-sim/<billet>.json` files was read by script (room, spot, step text). Spots were resolved through `equipKey` / `propsFor` (`js/equipment.js:101-104`) and compared with the props `js/gen.js` places in that room type.
3. **What the game tells the player an object is**: `assets/data/ship-items.json` `examine[room][propKind]` (built by `tools/build-game-items.mjs`, which maps game rooms to inventory spaces in `ROOM_SPACES`, line 7). When the examine text names a different machine than the prop shows, that is a stand-in.
4. **Inventory cross-check**: the 124 spaces in `docs/ship-inventory/*.json` were filtered to huge items and large floor-standing items; clutter names in `ship-items.json` were run through the keyword table `KW` in `js/itemart.js`.
5. A gap is listed only if the game references the thing (cited in the Evidence column) and no dedicated model exists. Priority: **A** = a scripted duty, a room's main hardware or a spot used by many billets has no model or the wrong one; **B** = noticeable (named in duty steps, system parts or examine text); **C** = polish (inventory only, or a variant). Size: **S** under ~300 triangles / up to 10 parts; **M** 300-1,200 triangles / 10-40 parts; **L** 1,200-3,000 triangles / 40+ parts. Type: prop (floor, `buildProp`), decor (wall fixture, `DECOR` kit), item (`buildItem`), cart (`makeCart`), wearable, clip, decal, structure, icon.

Three findings shape everything else:

* **One generic console stands in for about thirteen named stations.** `console` ("ops console", standing, `js/equipment.js:25`) is the spot of 519 crew-sim entries in 14 room types. Six room types whose billets are scripted to work a console get none from `js/gen.js`: transporter (34 entries), brig (17), holodeck (14), sickbay (13), shuttlebay (11), cargo (7).
* **Four `EQUIPMENT` entries are stand-ins by construction**: `bar` uses table / replicator / sofa (`:56`), `counter` uses replicator / table (`:94`), `stove` uses replicator (`:95`), `mat` uses weightbench / treadmill (`:96`). `bar` alone is in the daily template or activities of all 41 billets (82 entries).
* **The examine text contradicts the mesh** in several rooms: the plant-room `tank` is described as "Primary coolant pump 2" (centrifugal pump), the arboretum `tree` as "grow beds, NFT channel benches", the stores `crate` as "walk-in chiller box", the mess `table` as "servery counter, stainless, 6 m", the lounge `table` as "pool table" or "bar counter", the armory `weaponrack` as "power-cell charging rack, 40-bay".

## 12. Recommended build order

Rules for every batch:

* One agent owns one new file per batch. Nobody edits `js/world.js`, `js/gen.js`, `js/equipment.js`, `js/carry.js`, `js/main.js`, `js/sim.js` or `js/humans.js` in an art batch; a single integrator does the hook-ups afterwards (list under each batch).
* Props: proposed registry `js/propart.js` exporting `PROP_ART = {}` and `buildPropArt(kind)`; each batch adds its own module `js/propart-<batch>.js` that exports `{ kinds: { name: (m, helpers) => Group } }`, and the integrator adds one import line per batch to `js/propart.js` plus one line in `buildProp`'s `default:` branch (`js/world.js:367`). Follow `buildProp` conventions: origin at floor centre, front faces +z, fits a 2.5 m tile, set `userData.top` for climbable tops, shared materials only.
* Wall fixtures: `DECOR` kits are closures over the `Kit` class in `js/world.js`; new ones go in `js/decorart-<batch>.js` using the same `K.box / K.cyl / K.cone` calls (vertex colours, `+z` out of the wall, 0-3.2 m high) and are merged into `DECOR` by the integrator.
* Items: `js/itemart.js` `DEFS` is one object; to avoid two agents editing it, each batch writes `js/itemart-<batch>.js` exporting `DEFS_<BATCH>` and its `KW` rows in the format of `docs/itemart.md`, and the integrator spreads them into `DEFS` / `KW`. Budget: 500 triangles, chamfered boxes, no text.
* Carts: `js/cartart.js` exporting builders with the same `userData` contract as `makeCart` (`js/carry.js:118`).
* Wearables: `js/wearables.js`, attached with `pinToBone` / `bindSurface` from `js/humans.js`.
* Every batch adds its kinds to the viewer (`models.html?set=...`) and a line to `CREDITS.md` only if it brings in outside assets (none expected).
