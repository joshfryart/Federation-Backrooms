Radial quick-menu anatomy. One wheel, eight sectors, two rings: inner ring = category, outer ring = the choices inside it (appears on hover, labelled by icon + word, numbered when you use keys). Centre hub = what you are about to do. The dead zone in the middle means "cancel" on release. Sector 1 is always This: the verbs for the exact thing in the reticle.

How the three gestures map to one wheel

Flick (fast, mouse)

Hold Q. The hand moves ~1 cm toward an icon (past the dead zone, a gesture, not a target). The outer ring appears under the cursor; flick on to the choice. Release. 300 ms total after practice. Releasing on a category runs its default choice (marked with a dot).

Tap / click (slow, precise)

Tap Q (<0.2 s). The wheel pins and the OS cursor appears (pointer lock released by us, not by Esc). Click an icon, click the hub or press Esc to leave. This is also the touch and mouse-only path.

Number keys (no mouse)

While open: digit = category, second digit = choice, same digit twice = default. Backspace = back a level. Same muscle memory as the current J menu, but now two keystrokes deep at most.

Gamepad

Hold LB: right stick picks, release LB commits (left stick keeps walking, a real advantage over modal menus). D-pad L/R rotates, A confirms, B backs out.

Radio becomes contact cards; the log becomes a timeline. Cards carry what the text list could not: who (portrait), rank (pips), department (colour and letter), whether they can answer (status shape), how far away they are. A card is a target; the action tray under it holds the 4-6 things you can do with that person.

The full board (J) is a swim-lane timeline of the 20-minute watch: your rounds, mission tasks, what your crew is doing, and ship events as a band. Click a block for the actions on exactly that block. Compact HUD

Ring = how close the next window is (fills as it approaches), amber when due, red + pulse when overdue, cyan while working, purple when a subordinate has it, green when done. Number = minutes left or !. Pips = mission tasks (green done, amber now, red missed, hollow pending). Reduce-motion stops the pulse; colour is never the only cue (ring numerals, icon, pip fill).

Full board (J)

One rule: tap = panel or instant action, hold = wheel. Digits only mean anything while a wheel/panel/lift is open, so they never clash with movement. Nothing that exists today moves except J/H/K/L/B/V which gain a hold behaviour. White dot = changed. Click a key to inspect.

Accessibility checklist

  • Everything doable with mouse only: tap-pinned wheel + on-screen dock (toggle at top of this page) + clickable panels.
  • Everything doable with keyboard only: digits, arrows, Enter, Backspace, Esc; Tab order in panels.
  • Hold vs toggle for wheel keys (stagebar in Sandbox) for people who cannot hold.
  • Text size 80-160% (page header A-/A+); panels use rem. Game CSS must move off fixed px in panels.
  • Reduce motion: stops pulses/spin-in; the game already has body.reduce-motion and the media query, so reuse them.
  • Colour is never alone: status = shape + colour; dept = letter + colour; priority = icon shape + colour.
  • High-contrast toggle (header) raises borders and dims.
  • Sticky wheel deadzone/size sliders (sensitivity of flick) in Settings.

Diagnosis (js/main.js, js/hud-duty.js, js/hud-comms.js)

  1. J / H / K / L / talk / terminal menus are overlays only. They never leave G.phase === 'play' and never release pointer lock (hud-duty.js openMenu, hud-comms.js openPanel; main.js talkMenu, terminalMenu).
  2. The player presses Esc. The browser consumes it at UA level to exit pointer lock. Whether the page also gets the keydown is browser-dependent (Chrome often swallows it), so the page cannot rely on it either way.
  3. pointerlockchange (main.js:594-597) runs: locked=false, phase is still 'play', so it does G.phase='paused'; showScreen('pause'). There is no notion of "this unlock was expected".
  4. If the keydown was delivered, DutyHUD.onKey (hud-duty.js:63) or CommsHUD.onKey (hud-comms.js:136) closes the menu first: result = menu closes and pause opens. If swallowed, pause opens and the menu DOM stays up under it until the next key (onKey bails on ph!=='play'). Both match the playtest report.
  5. The tubelift panel is not affected: it calls exitPointerLock() itself (phase 'select'), so Esc arrives as a plain keydown and closeLiftPanel() re-locks inside that keydown gesture.

Fix: unlock on purpose, then Esc belongs to the page

if (!locked && G.phase === 'play') {
  if (UI.expectUnlock || UI.stack.length) { UI.expectUnlock = false; return }
  if (UI.wheelHeld) { UI.cancelWheel(); UI.needClick = true; return }

}

Three interaction models. A is recommended; B and C reuse most of A's pieces, so choosing A does not close the others off.

Recommended A · Hold-wheel + tap-panels

  • Fastest for the common acts (do duty, hail bridge, switch tool).
  • One mental model; letter keys keep working.
  • Pinned mode doubles as the mouse-only and touch path.
  • Cost: new DOM/SVG component + ui-mode state machine.

B Command mode (hold Alt = free cursor over the HUD)

  • No new component: existing HUD widgets become buttons.
  • Always-visible info is the menu (Fallout 76 / Rust style).
  • Needs screen real estate permanently; clutters the "calm ship" feel; slower for keyboard players.
  • Good fallback layer inside A (that is what pinned mode is).

C Diegetic PADD (hold Tab raises it)

  • On-theme; the PADD item already exists in handhelds.
  • One surface for all panels, easy gamepad nav.
  • Slow to reach (raise animation), not usable mid-sprint, and the world stays live behind a half-screen prop.
  • Best as the visual shell for A's panels, later.

Why A

  • Fixes the owner's three complaints directly: icons not text, no clunky key per sub-menu, and Esc stops fighting.
  • The game is a real-time walk-around; the quick path must not take the hand off WASD (Q/E/V/J/H are all left-hand).
  • It includes B (pinned wheel, dock) as its slow path and can host C later.
